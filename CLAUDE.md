# Easy Week — правила проекта

## Роутинг AI-моделей (главное правило)

**Каждую AI-задачу делает модель, выбранная пользователем.** Провайдеры: **DeepSeek**
(`deepseek-chat`), **Gemini** (`gemini-flash-latest`), **Claude** (`claude-haiku-4-5`, Anthropic API —
нужен баланс кредитов в console.anthropic.com), **Cloudflare** (mistral-пайплайн), **OpenRouter**
(`OPENROUTER_MODEL`, по умолчанию бесплатная `nvidia/nemotron-3-super-120b-a12b:free` — проба
дешёвых моделей на служебных задачах). В скобках — модель провайдера по умолчанию (`.env`).

**Конкретная модель провайдера** выбирается в настройках: значение задачи — ссылка «провайдер» или
«провайдер:id» (`services/model_catalog.py`: курируемый каталог, проверен по /models ключей
2026-09-30; модель из `.env` всегда первая; id OpenRouter содержит «:» — режем по первому).
Выпадашка в настройках — группы по провайдерам, внутри модели. Claude — только Haiku 4.5 и
Sonnet 5.5 (Opus/Fable не предлагаем — дорого). Страницы (чат/рецепт/готовка/покупки) выбирают
провайдера; голый провайдер бэк дополняет моделью задачи из настроек, если провайдер тот же,
иначе — моделью по умолчанию (`gates.resolve_ref`). Выбор → копия гейта с моделью
(`ModelGate.with_model`), ключ провайдера везде прежний (варианты, оценки, лимиты). У Cloudflare
выбор меняет главную модель (`main_model`/`menu_model`), спеки пайплайна — прежняя быстрая.
Особенности моделей в гейтах: DeepSeek `deepseek-flash`/`deepseek-v4-pro` — `thinking: disabled`
(иначе размышление съедает max_tokens и JSON пустой); Gemini `*lite*` — без `thinkingConfig` (400);
Claude 5.x/Fable — размышление всегда включено → `output_config.effort: low` + запас токенов и
таймаут 180 с, prefill/temperature не шлём. Цены — по конкретной модели («провайдер:id» в
`prices.json`), без своей строки — по цене провайдера.

**Дневных лимитов на Claude нет** (`ANTHROPIC_DAILY_PLANS/RECIPES` = 0 по умолчанию; включаются в
`.env`) — вместо них **статистика запросов**: Профиль → Модели, карточка «Запросы к моделям» за 7 дней
(`GET /api/settings/usage`, `services/usage.py`: из AI-логов — удачные вызовы, сбои-попытки, стоимость
по `cost_usd` записи или текущим ценам; разбор файла дня кэшируется по размеру/mtime).

**Модели по умолчанию — по задачам, на сервере** (общие для всех устройств семьи):
Профиль → «Модели по умолчанию» (`/settings/models`), `GET/PUT /api/settings`,
файл `backend/data/settings.json` (`services/settings.py`, атомарная запись, в `deploy/backup.sh`).

| Задача (`task`) | Что входит | Встроенный дефолт |
|---|---|---|
| `chat` — «Чат и план» | генерация плана, правки в чате, ответы в обсуждении | `RECIPE_MODEL_DEFAULT` |
| `recipe` — «Рецепты» | рецепт блюда (открыть/перегенерировать), догенерация рецептов для покупок/PDF/готовки | `RECIPE_MODEL_DEFAULT` |
| `shopping` — «Список покупок» | нормализация списка покупок (GET и ↻) | `cloudflare` |
| `cooking` — «План готовки» | единый план готовки | `RECIPE_MODEL_DEFAULT` |
| `prefs` — «Предпочтения из чата» | фоновое извлечение вкусов из сообщений чата (`ai/prefs.py`) | `cloudflare` |
| `summary` — «Сводка чата» | фоновая сводка беседы после реплик пользователя (`services/summary.py`) | `cloudflare` |

**Карта «задача → какие модели можно выбрать»** — `TASK_MODELS` в `services/settings.py`
(единственный источник; фронт получает её из `GET /api/settings` → `taskModels` и строит
выпадашки только из неё):

| Задача | DeepSeek | Gemini | Claude | Cloudflare | OpenRouter |
|---|---|---|---|---|---|
| `chat` | ✓ | ✓ | ✓ | ✓ (свой пайплайн) | ✓ (проба) |
| `recipe` | ✓ | ✓ | ✓ | ✗ | ✗ |
| `cooking` | ✓ | ✓ | ✓ | ✗ | ✗ |
| `shopping` | ✓ | ✓ | ✓ | ✓ | ✗ (путал количества) |
| `prefs` | ✓ | ✓ | ✗ (дорого/лимит) | ✓ | ✓ |
| `summary` | ✓ | ✓ | ✗ (дорого/лимит) | ✓ | ✓ |

Дешёвые модели (Cloudflare, OpenRouter) плохо пишут длинный связный JSON — развёрнутые рецепты
и план готовки им не предлагаем. Бесплатные OpenRouter сняты и с покупок: склеивали неверно
(рис 160 + «рис белый» 100 г, лук 650 → 750 г, яйца в двух группах — 👎 2026-10-09). Правила карты: `PUT /api/settings` с неподходящей парой → 422;
`get_models()` игнорирует сохранённое раньше неподходящее значение; `resolve_key(model, task)`
явную неподходящую модель (старый клиент, внутренний шаг вроде правки рецепта моделью чата)
заменяет дефолтом задачи с warning в лог — это политика выбора, а не фолбэк по сбою.
Уже сгенерированные варианты рецепта/готовки «запрещённой» моделью остаются открываемыми
(переключение на существующий вариант карте не подчиняется, новых такой моделью не делаем).

Страница может выбрать другую модель локально (не меняя настройки): чат — override на этот чат,
рецепт/готовка — выпадашка вариантов, покупки — выпадашка в шапке (для ↻). Запрос без модели
(`recipeModel: ""`) → бэк берёт дефолт задачи: `gate_for(model, task)` / `resolve_key(model, task)`
в `ai/gates.py`. Явно переданная модель всегда важнее дефолта.

**Фолбэков между моделями НЕТ.** Выбранная модель либо отвечает, либо кидает `AIError` →
роутер отдаёт 502 / `event: error`, и фронт просит переключить модель или собрать план заново.
В чате под последней репликой пользователя — «↻ Переотправить · Модель» (GUIDEBOOK «Переотправить»):
тот же запрос (новый план / правка / обсуждение) моделью из шапки; запрос с `resend` — сервер не пишет
реплику второй раз (`history.is_repeat`), `event: error` потока несёт `conversationId` (повтор — в ту же беседу).

**Список покупок** — детерминированная база из ингредиентов + нормализация моделью задачи
`shopping` (по умолчанию Cloudflare mistral `@cf/mistralai/mistral-small-3.1-24b-instruct`
со строгой json_schema; DeepSeek/Gemini/Claude — JSON-режим, форма ответа в `SHOP_SYSTEM`).
Сбой нормализации в GET — отдаём базу без кэша (это не подмена модели), в ↻ — 502.
**Количества считает код, не модель:** строки базы пронумерованы, модель только склеивает, называет
и раскладывает по отделам (`from` — номера строк), сумма — `shopping.reconcile_normalized`
(строка базы — в одну позицию; без `from` — по основе названия, иначе выдумка и мимо; потерянные
моделью строки возвращаются, кроме ↻ с обсуждением — там «убери соль» законно). Детерминированно:
яйца/«яйца куриные» — одна позиция в «Молочном», свежая зелень — «Овощи», вода/кипяток в покупки не
идут (`fix_category`/`is_water` — в базе и на отдаче, чинят и старые кэши); рецепт называет зелень
(«укроп», «петрушка»), а не «зелень». Причина — 👎 2026-10-09 (рис 160 + «рис белый» 100 г, лук
650 → 750 г, яйца в двух отделах).
Фоновое извлечение предпочтений (`ai/prefs.py`) — модель задачи `prefs` (Cloudflare — со схемой,
остальные — JSON-режим и few-shot). **Три уровня уверенности:** стопроцентное и постоянное («не ем»,
«терпеть не могу», «никогда не предлагай», общее «люблю X») → сразу в `dislikes`/`likes`
(«больше никогда не предлагать»); «похоже на вкус» → только подсказки `suggested_dislikes`/
`suggested_likes` («Это ваш вкус?» на `/preferences`, переносит пользователь, в промпты не идут);
разовое («на этой неделе без рыбы», «убери X», «не хочу») → никуда (в чате его держит память
беседы). Страховки без модели: экстрактор зовём только при словах про вкус (`has_taste_marker`),
разовые маркеры без слов про постоянство и отзывы «понравилось/вкусно» — максимум подсказка,
продукт должен быть в тексте (`_grounded`; продукт из коротких слов — «щи» — целым словом или
падежом, раньше молча отбрасывался). Пожелание к кнопке замены/добавления — разовое, экстрактор
только при словах про постоянство (`has_permanent_marker`: «макс не любит тыкву вообще»). Прогон на реальной модели: 21/22, ложных «никогда» — 0. Все AI-контексты выбираются в настройках; вне выбора остаются
только под-модели внутри Cloudflare-пайплайна (`CF_MODEL*` в .env — это внутренности одного
провайдера, а не отдельная задача).

Провайдеры логируются с меткой: `AI → DeepSeek · …` / `AI → Gemini · …` / `AI → Cloudflare · …` /
`AI → OpenRouter · …`.

**Свои покупки (мимо рецептов)** — «ещё хлеб, йогурт домой»: Покупки → «Добавить» (футер) → модалка
со свободным текстом → `POST /api/plans/{id}/shopping-list/extras` (`text`, `recipeModel` — выпадашка
страницы, пусто → дефолт задачи `shopping`) → `planner.parse_shopping_extras` (`SHOP_EXTRAS_SYSTEM`:
один товар — одна позиция, только названное, количество — только если сказано, иначе 0; отделы
рецептов + «Фрукты» / «Хлеб и выпечка» / «Напитки» / «Хозтовары») → чистка `shopping.clean_extras` →
`PlanRow.shopping_extras` (слияние `merge_extras`: тот же продукт и единица — количества складываются).
В список они идут отдельно от кэша нормализации (`group_items(..., extras)`, флаг `extra`, в «Есть
дома» не уходят) — ↻ и GET их не трогают; PDF тоже с ними. Удаление — `DELETE …/extras/{id}` (чипы в
модалке). Правка плана в чате переносит их в новую версию (свежими из базы). Сбой модели — 502,
ничего не пишем. Прогон (4 списка, 19 позиций): OpenRouter nemotron / DeepSeek / Cloudflare — 19/19.

**Остатки «пристроить, чтобы не пропали»** («остался порей, сельдерей…») — ингредиенты, а не тема
меню. Правило `_LEFTOVERS_RULE` в промпте плана (`ai/prompt.py`): сначала настоящие общеизвестные
блюда, остатки — туда, где они в классическом рецепте; не выдумывать блюдо ради остатка, не
перечислять остатки в названии, пристроить все — не цель (лишние честно не пристраиваем). Модель
возвращает `leftovers` (план → `PlanRow.leftovers`) и `uses` у блюда; куда ушли остатки — показывает
карточка плана по `uses` (строка «🧺 Остатки», `♻` под блюдом), а не проза reply. **Остатки и `uses` —
только названные пользователем:** `planner._ground_plan` оставляет те, чья основа слова есть в его
репликах беседы (`prefs.grounded`, роутер передаёт `user_text`) или в уже известных остатках плана;
фразы реплики про выдуманные вырезаются (в потоке — событие `reply` после `meta`, фронт заменяет текст
по `done.reply`). Причина — 👎 2026-10-05: Haiku на «В день подачи» «пристроила остатки творога и
колбасок» из «недавно ели» и книги рецептов. В user-промпте плана/блюда служебные блоки (недавно ели,
книга, разнообразие, неделя, вкусы) — под `SERVICE_HEADER` «это НЕ слова пользователя», реплика —
по `_REPLY_RULE` (не приписывать ему «надоело», «без картошки»). Деталь рецепта
получает только `uses` своего блюда, и то как совет: берёт лишь то, что входит в классический
состав (Haiku вешала оливки «закуской» на котлеты по-киевски); предложения реплики плана про
остатки из «что обещано — выполни» вырезаются. Есть рецепт — `uses` пересчитываются по его
ингредиентам (`shopping.sync_uses`), карточка показывает правду; замена/добавление блюда —
ещё не пристроенные (`free_leftovers`), правка плана — статус остатков в контексте. В покупках
позиции-остатки уходят в группу «Есть дома (остатки)» последней (`services/shopping.is_leftover`:
формы слова — да, производное вроде «оливковое масло»/«томатная паста»/«лук-порей» для «лук» — нет).
Прогон исходного запроса: DeepSeek/Gemini — настоящие блюда (солянка, тажин, рассольник), Haiku
слабее (лепит остатки в выдуманные блюда) — для такого запроса лучше DeepSeek/Gemini.

**Задумка блюда** (`desc`) — модель плана пишет к каждому блюду 1–2 предложения: блюдо в
классическом виде (основа, способ, соус), без подачи/гарниров/закусок (`_DESC_RULE`). Идёт в
промпт рецепта («Задумка блюда из плана» в `_dish_header`) — рецепт опирается не только на
название; видна пользователю: в чате — одной строкой с «развернуть» (`ew-clamp`), на странице блюда — целиком.

**Заготовка и «свежее»** — правила в общем префиксе промптов (`FREEZE_RULES`, `ai/prompt.py`; по
мотивам промпта пользователя про meal prep): главное — вкус и текстура в момент еды, заморозка —
инструмент; каждый компонент — морозилка / холодильник / заготовить и довести в день подачи / добавить
свежим. В день подачи: паста, картофель, готовая рыба (рыбу готовим в день подачи, морозим соус и
сырое филе), свежая зелень и овощи, хрустящее. Крупы морозить можно (недоварить на 1–2 мин), соусы
стабилизируем Е1422 (он есть дома). День заготовки не фиксируем (не «суббота»).
**Режим блюда** — `storage.freeze`: по умолчанию заготовка ❄️ (`shelf_life_days` — дни в морозилке,
7–180); «свежее» 🌿 (`freeze=false`, дни в холодильнике 0–5, 0 — съесть сразу) — ТОЛЬКО по просьбе
пользователя («план на неделю, а сегодня хочу салат», «на 2–3 дня свежим», «не морозить»; сам названный
салат из свежих овощей) — `_MODE_RULE`, нормализация `planner._clean_storage` (сомнительное — заморозка).
У Cloudflare режим ставит меню (`fresh`/`fresh_days` у блюда), спекер блюда — всегда заготовка (он
видит весь запрос, а не своё блюдо). Режим идёт в шапку рецепта (`_mode_line`) и в план готовки:
`fresh`-продукты и свежее «съесть сразу» — последняя фаза «В день подачи» (не в общее время), свежее
«в холодильнике N дн» готовится в заготовке без заморозки. **Что не морозится — помечено в самом рецепте:** ингредиент
`fresh: true` (🌿 на странице блюда; `_clean_ingredients` оставляет только явное true; продукт — одной
строкой, по ним считаются покупки) + `note` — памятка строками «Морозилка: / Холодильник: / В день
подачи: / Разогрев: / Важно:» (фронт разбирает `parseStorageNote`, `shared/storage.ts`; старые заметки
без меток — абзацем). Прогон DeepSeek: болоньезе 3/3 (спагетти/пармезан/базилик 🌿, соус с Е1422), рыба
5/6 — готовится в день подачи, салат «на сегодня» → 🌿, остальные блюда ❄️; Gemini не прогнан (квота).

**Книга рецептов семьи** (`services/recipebook.py`) — блюда принятых планов с рецептом. Названия
идут в промпт плана (не подсказка меню — чтобы узнать блюдо, названное пользователем: «начинка
для Chicken Pod Pa, она уже есть в рецептах»); явно названное блюдо важнее «недавно ели». Блюдо
нового плана с тем же названием (норм. название, падеж/опечатка — то же число слов и сходство
≥ 0.9) сразу получает рецепт из книги (все варианты, `from_book`) — без генерации, если режим тот же
(❄️/🌿 — шаги рецепта разные; «а сегодня салат», а в книге он заготовкой → соберёт модель); свой рецепт —
всегда, режим задаёт он.

**Свой рецепт** (Книга → «📝 Свой рецепт», `routers/recipes.py`): модалка с текстом →
`POST /api/recipes/improve` («Улучшить»: тот же рецепт понятным текстом, без выдумок; «Откатить» —
на фронте) → `POST /api/recipes/custom` («Дальше»: полный рецепт под заморозку СТРОГО по тексту +
шапка — `CUSTOM_RECIPE_SYSTEM`, общие правила единиц/шагов с рецептом блюда). Модель — выпадашка
в модалке (`recipeModel`; старт — дефолт задачи `recipe`, выбор только для этого рецепта, настройки
не меняет). «↻ Перегенерировать» на странице рецепта сначала спрашивает «Что учесть?» (`DetailRequest.note`
→ `change` в `regenerate_dish`, обязательная правка варианта); у своего рецепта уточнение
дописывается к `source` («Уточнение: …»). Хранится блюдом служебного плана «Мои рецепты» (`recipebook.library_row`, id/беседа/статус
`library`): страница рецепта, варианты, ↻, озвучка — как у плана; в списке планов его нет, в
«Рецептах» — первым. `dish["source"]` — текст пользователя: любая перегенерация держится его
(`prompt._source_block`). Свои рецепты — в книге рецептов: план и «добавь/замени» в чате берут их
по названию готовыми (`attach`, вместе с `source`).

**«Добавить блюдо» списком** (`planner.add_dish_direct`): «жаркое, суп с фрикадельками, салат
крабовый» (запятые/строки, каждая часть похожа на название — `split_dish_list`, до 6) → каждое
блюдо отдельным промптом на одно блюдо, параллельно; не вышло одно — остальные добавлены, в ответе
сказано, что нет. Уточнения через запятую («лёгкое, без рыбы», «суп, но не борщ») — одно блюдо.

**Быстрый выбор плана** (новый чат, только фронт — `shared/plan-wizard.ts`): карточки-шаги →
первое сообщение «Ужины · 5 блюд · до 30 минут · основа: птица, рыба», а дописанный текст — второй
строкой «Уточнение (важнее выбора выше): …» (текст пользователя приоритетнее карточек). Число блюд —
из шага (dishes_count), выпадашки числа в шапке чата нет; явное число в тексте важнее (промпт
плана). Выбор разовый: формулировки без слов «люблю/нравится» — экстрактор предпочтений мимо.

**Память беседы в чате** — в КАЖДУЮ генерацию чата (новый план `/chat` и `/chat/stream`, правки
`/chat/edit`, обсуждение `/chat/discuss`) идут первое сообщение пользователя («с чего начался чат»)
и последняя сводка беседы, если она есть (`summary.memory()` / `prompt.chat_memory_block`;
на старте чата первое сообщение — это сам запрос, не дублируем). Сводка — `services/summary.py`:
после каждой реплики пользователя `schedule(conv_id)` → через 5 с тишины (дебаунс: новая реплика
раньше — таймер заново) моделью задачи `summary` пишется ОДНА сводка беседы
(`Conversation.summary`, перезаписывается; `summary_upto` — последнее учтённое сообщение, дальше
инкремент «прошлая сводка + новые реплики»). Пока в беседе одна реплика пользователя — сводки нет.
Сводка — только слова пользователя (`SUMMARY_SYSTEM`): состав плана и операции над ним (реплики
кнопок «Добавить блюдо…»/«Замена «…»», подтверждения «Готово: …» — `summary._OP_PREFIXES`) в промпт
не идут, вопросы ассистента — не решения пользователя, «одобрил/не хочет» — только сказанное прямо,
искажённое голосовым вводом не толкуем. Причина — сводка писала «добавлены суп, жаркое, салат»
(добавлен только суп), «одобрил уху», «не хочет мегрельские рецепты» — и это шло во все промпты.
Таймеры в памяти процесса (uvicorn без воркеров); лог — метка «сводка беседы», `endpoint=chat_summary`.

**Озвучка шагов (TTS)** — `ai/tts.py` + `GET /api/tts?text=…` (`routers/tts.py`): OpenRouter
`POST /audio/speech`, бесплатная `fish-audio/s2.1-pro-free:free` (русский, mp3; модель/голос —
`OPENROUTER_TTS_MODEL` / `OPENROUTER_TTS_VOICE`). В настройки не выведено — провайдер один.
**Голос обязателен** (`alloy` по умолчанию): без `voice` Fish берёт случайного диктора на каждый
шаг; из OpenAI-имён через OpenRouter принимает только `alloy` (стабильный мужской).
**Лимиты:** свой дневной лимит `TTS_DAILY_LIMIT` (20 генераций в сутки; кэш не считается; бронь
до вызова + возврат при сбое — `ai/limits.tts_*`, файл `usage-limits.json`, счётчик в `/api/limits`
→ строка в настройках моделей). Бесплатные модели OpenRouter — 50 запросов в сутки на аккаунт на
ВСЕ `:free`-модели (озвучка + покупки + предпочтения; $10 кредитов → 1000/сутки): на 429 запоминаем
«заблокировано до» (дневной — до `X-RateLimit-Reset`, перегрузка пула — 20 с) и в OpenRouter не
ходим; `/api/tts` → 429 + `Retry-After` с понятным текстом, `GET /api/tts/status` — причина для
фронта (`<audio>` текст ошибки не видит), прогрев на 429 останавливается.
Кэш `data/tts/<sha1(модель·голос|текст)>.mp3` (не бэкапим), параллельные запросы одного шага
склеиваются, `Cache-Control: private, no-cache` + ETag (смена голоса видна сразу; `r=` в URL
фронта — одноразовый сброс старых 30-дневных записей). **Прогрев — на фронте** (`TtsPlayer`): первый тап в
рецепте/плане готовки ставит остальные шаги в очередь, плеер тянет их тем же GET по 2 параллельно
(порядок — от нажатого по кругу) и держит аудио в памяти (blob URL, до 80 штук) — следующие тапы
стартуют без сети; пока шаг качается, его кнопка пульсирует (`warming`), готовый — оранжевый
(`readyKeys`). Во время игры на кнопке кольцо прогресса + остаток времени; внизу панель плеера
`ew-tts-panel` (▶/❚❚, дорожка с перемоткой, режим «Один шаг» / «Подряд», ×), Media Session для
экрана блокировки. Вёрстка — GUIDEBOOK «Озвучка шага» / «Панель озвучки». Фронт: `ew-tts-btn` (`shared/tts-btn.ts`) +
общий плеер `TtsPlayer` — `audio.src` + `play()` синхронно в тапе (иначе iOS не играет), поэтому
GET с текстом в query, а не POST. TTS-модели OpenRouter в общем каталоге `/models` не видны
(`deepgram/flux-tts:free` — только английский, требует `voice=flux-*-en`).

### Архитектура (гейты)
Наглядная схема (потоки + классы + матрица задач) — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).
Каждый провайдер — подкласс `ModelGate` (`ai/base.py`): `complete_json` (шаблонный метод с
ретраями/логом), хуки `_request_json`/`stream_json`/`call_tools`. Реестр и выбор — `ai/gates.py`
(`gate_for(model_key, task)` — пустой ключ → дефолт задачи). `ai/planner.py` роутит по выбранной модели, без `try/except → другой провайдер`.
- DeepSeek/Gemini/Claude — план одним запросом; Cloudflare — пайплайн меню→спеки→валидатор.
- Правки: DeepSeek — function calling; Gemini/Claude/Cloudflare — structured actions.
  `edit_dish` (правка рецепта в чате) кладёт вариант под ключ модели, РЕАЛЬНО писавшей рецепт
  (`detail["model"]`, гейт задачи `recipe`), а не модели чата.
- Gemini: `thinkingBudget=0` (рецептам reasoning не нужен, иначе обрывает JSON).
  503/5xx/429 без квоты — `AIOverloaded`: повтор через 2–6 с с разбросом (`overload_backoff`, сна ≤ 20 с,
  RetryInfo/Retry-After уважаем); квотный 429 — `LimitError` (→ 429) без повтора + «заблокировано до» по
  модели (дневная — до полуночи PT). 4xx, SAFETY/MAX_TOKENS — без повтора; битый JSON и тело ошибки — в JSONL.
- Claude: system — отдельным полем; температуру не шлём (Opus 4.8/4.7 её отвергают); JSON-режима
  нет — просим строгий JSON в промпте и лениво парсим (снимаем ```-ограждение).
- Новый ключ Google не даёт `gemini-2.5-flash` — используем алиас `gemini-flash-latest`.
- OpenRouter (`ai/openrouter.py`): OpenAI-совместимый, `response_format: json_object` +
  `reasoning.enabled=false` (иначе reasoning съедает max_tokens и рвёт JSON), ленивый парсер
  `loads_lenient` (общий с Claude, в `ai/base.py`); стрима/tools нет. Ошибка может прийти телом
  при 200 — проверяем `error`. Бесплатные модели: ~20 запр./мин и дневной лимит, upstream-429
  бывает часто — это `AIError`, а не повод для фолбэка. `respan/span-01-lite:free` — модель
  «decisions» (скоринг), chat/completions не умеет — для генерации не годится.

### Хранение рецептов в плане (запись — только `services/planstore.py`)
- `planrow.dishes` и `cooking_plan` пишет **только** `services/planstore`: `patch_dishes(session,
  plan_id, changes={dish_id: fn} | append=…)` перечитывает строку из БД прямо перед записью (мимо
  identity map, без await между чтением и записью), меняет только свои блюда по id и пишет UPDATE
  с CAS по `planrow.dishes_version` (3 попытки → `PlanConflict` → 409; `PlanNotFound` → 404,
  обработчики в `main.py`); `new_row` — новая строка плана; `carry_current` — версия после
  правки в чате берёт нетронутые правкой блюда из родителя НА МОМЕНТ записи; `patch_cooking` —
  вариант плана готовки вливается в свежий кэш. `row.dishes = …` / `PlanRow(dishes=…)` вне
  planstore запрещены тестом (`tests/test_planstore.py::test_no_direct_plan_writes`).
- Каждый НОВЫЙ вариант рецепта (`services/variants.with_detail` / `variant_from_detail`, `kind`
  обязателен) несёт метаданные: `model_ref` (точная «провайдер:id», `gates.model_ref`), `kind`
  (generate | regenerate | chat_edit | discuss_edit | backfill | custom), `change` (уточнение
  «Что учесть?» / правка), `parent_id` (ключ варианта, от которого шли), `ctx_uses` (остатки
  плана при генерации), `gen_id` (id генерации; он же в AI-логе — `observe.ai_scope`). Деталь
  модели (`generate_dish_detail` / `generate_custom_recipe`) отдаёт `model`/`model_ref`/`gen_id`.
  Догенерация (покупки/PDF/готовка) — тоже вариант (`kind backfill`), плоских «ничьих» деталей нет.
- «Мои рецепты» (план/беседа `library`) — не план недели: DELETE/PATCH/status → 409, правка в
  чате служебный план не берёт (`_latest_plan`), `/chat/edit` в беседе `library` без черновика
  плана → 409; `history.original_request('library')` → `''`.

### Таблицы рецептов (фаза 1: двойная запись, чтение — по-прежнему JSON)
- `recipe` (рецепт блюда: линия версий плана / свой рецепт) и `recipe_revision` (неизменная версия
  текста, триггер `recipe_revision_immutable`) — `models.py`, своя MetaData
  (`RECIPE_METADATA`): `init_db` их НЕ создаёт. Создаёт и наполняет только CLI
  `python -m app.migrations` (`app/migrations/recipes_v1.py`, маркер `recipes_v1` в
  `schema_migration`); он же добавляет `ratingrow.recipe_id/revision_id`,
  `favoriterecipe.recipe_id`, `messagerow.recipe_id` (не поля ORM — пишутся Core-UPDATE).
- Блюдо плана получает только `recipe_id` + `rev_ids` ({модель: id версии}); остальной JSON не
  меняется и остаётся источником для чтения. Логика — `services/recipestore.py` (логгер
  `easy_week.recipes`): id детерминированы (uuid5 от ключа линии `lin:<первое появление>/<dish_id>/
  <name_key>` / `own:<id>` и от рецепт|модель|content_hash|meta_hash), правила поиска рецепта —
  `recipe_for` (никогда только по dish_id или только по названию).
- При маркере `planstore.patch_dishes` / `new_row` в той же транзакции вызывают
  `recipestore.dual_write*` в SAVEPOINT: сбой → ERROR + метрика, JSON всё равно пишется,
  догоняет `migrations sync`. Новые 👍/👎 рецепта, ★ и реплики обсуждения рецепта пишут
  recipe_id/revision_id (поиск — пока прежний). На старте — сверка только на чтение → `/api/health`.
- `hydrate_rows` / `book_entries` (чтение из таблиц) пока только для сверки V1–V10 и фазы 2.

## Наблюдаемость и логирование (где что)

Чтобы не искать заново — куда логировать и как смотреть.

- **AI-вызовы (любой провайдер)** идут через `ai/observe.log_ai_call(...)` (вызывается внутри
  `ai/deepseek.py` и `ai/cloudflare.py`). Он делает сразу три вещи:
  1) консольный лог (логгер `easy_week.ai`) → journald;
  2) строку JSONL в файл-за-день `backend/data/ai-logs/ai-YYYY-MM-DD.jsonl` — для анализа.
     Поля: ts, provider, model, label, `ok` (true/false), `duration_ms`, usage/кэш, messages,
     response (на успехе) либо `error`+`attempt` (на неудачной попытке), плюс корреляция запроса —
     `conversation_id`/`plan_id`/`dish_id`/`endpoint`/`action` (+ `gen_id` генерации рецепта —
     он же в варианте рецепта; `recipe_id` — задел). Контекст корреляции выставляет
     роутер через `observe.set_ai_context(...)` (contextvars, без протаскивания через гейты);
  3) Prometheus-счётчики `easyweek_ai_calls_total` / `easyweek_ai_tokens_total{kind=…}` /
     `easyweek_ai_errors_total`.
  **Новый AI-вызов логируется сам, если идёт через хелперы deepseek/cloudflare.** Не дублировать.
- **Обычные логи приложения:** `logging.getLogger("easy_week.<модуль>")` (INFO) → stdout → journald
  (`journalctl -u easy-week-backend`). Свой логгер не изобретать.
- **Метрики:** `/metrics` (prometheus-fastapi-instrumentator). На Пае проброшен nginx: `:8080/metrics` (только LAN/tailnet/localhost).
- **Стек мониторинга — в `monitoring/`** (Prometheus + Loki + Promtail + Grafana). Локально —
  через Docker из `docker/` (см. ниже), на Пае native (`monitoring/install-pi.sh`).
  Grafana на Пае: `http://192.168.1.230:3002`. Логи смотреть в Grafana → Explore → Loki:
  `{job="easy-week-ai"}` (AI-вызовы) или `{job="easy-week-backend"}` (сервис).

## Docker (локальный запуск всего из одного места)

Все docker-конфиги — в **`docker/`** (compose + Dockerfile'ы). Запускать оттуда: `cd docker`.
- `docker compose up -d --build` — бэкенд + фронт (порт 8080).
- `docker compose --profile monitoring up -d --build` — то же + Prometheus/Loki/Promtail/Grafana.
- Dev-оверрайд (`docker-compose.override.yml`) подхватывается сам: бэкенд `--reload` + монтирование кода.

Один compose-проект `easy-week`: приложение и мониторинг в общей сети и на одном томе
`easy-week_ewdata` (AI-логи), поэтому мониторинг просто профиль — без external-сети/тома.
Build-контексты остаются `backend/` и `frontend/` (там `requirements.txt`/`package.json`),
Dockerfile'ы вынесены в `docker/*.Dockerfile`. Конфиги самих сервисов мониторинга
(`*.docker.yml`, дашборды) остаются в `monitoring/` рядом с нативным Пай-деплоем и монтируются
из compose. На Пае — по-прежнему native (systemd), не через этот compose (см. `deploy/README.md`).

## Деплой на Raspberry Pi (после каждого коммита)

Каждый коммит **сразу катим на Пай**. Деплой — через git + SSH:

```bash
git push                                   # запушить коммит(ы)
ssh pi5 'cd ~/easy-week && bash deploy/update.sh'
```

- SSH-хост — алиас **`pi5`** (пользователь `pashtitto`, каталог `~/easy-week`), ключ настроен —
  пароль не нужен. Прямой `pashtitto@192.168.1.230` без ключа не пускает — используем `pi5`.
- `deploy/update.sh` делает всё: бэкап (`deploy/backup.sh` → `easy-week-predeploy-*`, ротация
  отдельно от ночных; упал — деплой стоп, осознанно без него — `EW_SKIP_BACKUP=1`) →
  `git pull --ff-only` → бэк (venv+pip) → `python -m app.migrations rehearse` (репетиция миграций
  на копии базы; провал — стоп ДО сборки и рестарта) → фронт (`npm ci && npm run build`) →
  `systemctl stop` → `migrations apply --live` (своя копия; новые колонки моделей приложения; шаг одной транзакцией, сверка, затем sync)
  → `systemctl start` ВСЕГДА (trap; сбой миграции — ненулевой код 1/2/3 и `status --live`) →
  `nginx reload`. Изменился сам `update.sh` в pull — перезапускается новой версией (`exec`);
  первый деплой фазы 1 — `git pull --ff-only && bash deploy/update.sh` (скрипт фазы 0 этого не
  умеет). Команды миграций, защита живой базы (в т.ч. из worktree) и откат L0–L4 —
  `deploy/README.md`.
  Копия бэкапа вне Пая, учебное восстановление и уровни отката — `deploy/README.md` → «Откат».
- Локально в сети: `http://192.168.1.230:8080`. Логи: `ssh pi5 'journalctl -u easy-week-backend -f'`.
- **HTTPS/офлайн PWA:** service worker не регистрируется по LAN-http → офлайн не работает. Решение —
  **Tailscale Funnel**, поднят: `https://pashtitto.tail36c191.ts.net` → `127.0.0.1:8080`
  (`tailscale funnel status`), см. `deploy/README.md` шаг 6. PWA установлена с этого адреса
  (SW/кэш привязаны к origin).
- Полное описание (первичная настройка, Tailscale/Cloudflare) — `deploy/README.md`.
